3. Architecture: data, rendering, build output

We reused the existing content system. Article data is the ingredient list; React components are the recipe; Vite prepares the production package.

  1. Journal records export text, metadata, and relationships.
  2. The Journal index and dedicated article page read the same records.
  3. Both pass sections into the shared JournalBody renderer.
  4. The browser requests PNGs from public image paths.
  5. The build derives route-specific metadata and fallback HTML.
  6. Approved visuals are separately exported into a three-page PDF.

Article records

FN 11 lives in src/app/pages/Journal.tsx inside the exported journalEntries array.

export const journalEntries = [
  {
    label: "Field Note 11",
    slug: "why-automated-fixes-break-production-systems",
    title: "Why automated fixes break production systems",
    readTime: "6 min read",
    dateISO: "2026-10-25",
    comingSoon: false,
    sections: [
      "I pushed a documentation edit. CI went red.",
      // Remaining paragraphs and image references…
    ],
    relatedLinks: [/* Existing Journal and Lab destinations */],
  },
];
  • sections is ordered; its order becomes the reading order.
  • comingSoon: false makes the record available through the existing published-content workflow.
  • relatedLinks explicitly connects the article to other pages.
  • readTime is editorial metadata, not an automatically measured duration.
  • journalStrongLines identifies entire paragraphs for emphasis.

We did not add a general Markdown parser. Writing **bold** inside an ordinary string does not automatically make those words bold.

5. Rendering techniques and image safety

An image is represented in article data using a restricted string format:

![Description of the evidence.](/images/journal/fn-eleven-dependency-fix.png)

JournalBody recognizes that format and creates a real image element. Its image rule accepts local /images/journal/ paths, restricted filenames, and SVG/PNG/WebP extensions.

Ordinary text goes through React, which escapes displayed text. Supported explicit HTTPS links become anchors. The component does not interpret arbitrary HTML from article strings.

Scope of this protection: this is a restricted renderer for repository-controlled content. It is not a general-purpose sanitizer for arbitrary uploaded HTML or SVG.

Compact presentation without changing other articles

type JournalBodyProps = {
  sections: string[];
  compactImages?: boolean;
  subheads: ReadonlySet<string>;
  strongLines: ReadonlySet<string>;
};

export function JournalBody({
  sections,
  compactImages = false,
  subheads,
  strongLines,
}: JournalBodyProps) {
  // Existing rendering behavior…
}

The question mark makes the prop optional. The default false preserves existing image presentation unless a caller opts in.

<JournalBody
  sections={entry.sections}
  compactImages={
    entry.slug === "why-automated-fixes-break-production-systems"
  }
  subheads={journalSubheads}
  strongLines={journalStrongLines}
/>

We enabled the prop in both the dedicated article and expanded Journal preview. Fixing only one would leave inconsistent behavior.

<figure
  className={
    compactImages
      ? "mx-auto w-full max-w-[560px]"
      : undefined
  }
>
  {/* Image and optional full-size link */}
</figure>
ClassEffect
mx-autoCenter horizontally.
w-fullUse the available width on narrow screens.
max-w-[560px]Stop growing beyond 560 px.
h-auto on the imagePreserve the image’s proportions.

Full-size links preserve access to small source-code details:

// imagePath represents the local path extracted by the renderer.
<a
  href={imagePath}
  target="_blank"
  rel="noopener noreferrer"
>
  View full-size image (opens in a new tab)
</a>

The link announces the new tab. The rel values restrict opener access and referrer information.

Tradeoff: a slug check is a small targeted solution. If many articles need different layouts, explicit presentation metadata will scale better than accumulating slug checks.

Remaining improvements: intrinsic image width/height attributes could reserve space during loading. Text transcripts would make evidence more accessible and easier to read on small screens. Full-size links help but do not solve every accessibility issue.

7. SEO, prerendering, and integrations

The production build runs two stages:

vite build && npm run prerender:seo

The prerender script uses Vite to load exported content:

const { journalEntries } =
  await vite.ssrLoadModule("/src/app/pages/Journal.tsx");

It derives route metadata from published records:

journalEntries
  .filter(entry => !entry.comingSoon)
  .map(entry => ({
    path: `/journal/${entry.slug}`,
    title: `${entry.label}: ${entry.title} | h777 Journal`,
    description: entry.excerpt,
    date: entry.dateISO,
  }));

This provides route-specific metadata and fallback HTML before React runs. It does not fully server-render every paragraph and image of the React article. FN 11 was also added to the sitemap and the SEO validator’s expected route/schema records. The build generated 25 public route files.

9. The battlefield: bugs, surprises, and triage

Triage means classifying the problem before choosing a fix. Think of it as locating the leak before replacing the plumbing.

  1. Read the exact failure and identify the affected layer.
  2. Compare expected behavior with the implementation and environment.
  3. Form one specific diagnosis.
  4. Make a targeted correction.
  5. Rerun the affected check, then relevant regressions.

Gotcha 1 — A section link failed a route test

Symptom: Expected /lab#role-aware-maintenance-lanes to match a known route.

Root cause: the test compares complete strings against known routes and does not separate the pathname from its fragment. Browsers support the URL, but the test’s model does not recognize it.

Fix: use the supported /lab destination.

Future improvement: validate pathnames and fragment targets separately. Do not weaken assertions merely to make a test green.

Gotcha 2 — Browser capture blocked local files

Symptom: net::ERR_BLOCKED_BY_ADMINISTRATOR for a file:// URL.

Root cause: browser policy blocked local-file navigation.

Fix: serve the HTML using a temporary local HTTP server, then capture it using Playwright and Chromium. We changed delivery without weakening policy.

Gotcha 3 — The third carousel card overflowed

Symptom: the slide’s content height exceeded its fixed portrait canvas.

Root cause: code, verification excerpts, explanations, and footer required too much space.

Fix: adjust typography and spacing, capture again, assert that the container does not overflow, and visually inspect the result.

Gotcha 4 — Static HTML did not contain the article ending

Symptom: an assertion could not find the closing sentence in generated static HTML.

Root cause: the assertion assumed the prerendered fallback included the complete React article.

Fix: verify metadata in generated HTML, content in the exported record, and rendered text in the browser. Test each layer against its actual responsibility.

Gotcha 5 — Images were editorially oversized

Symptom: you reviewed the live article and found that the visuals dominated the writing.

Root cause: tall portrait evidence cards filled the article width.

Fix: optional compact layout, 560 px cap, and full-size links. This was a presentation issue, not a failed image request.

Gotcha 6 — The copy import missed an insertion anchor

Symptom: a temporary script reported ValueError: … is not in list.

Root cause: an exact-match anchor represented only the start of a longer uploaded paragraph.

Fix: match the paragraph prefix. The failed attempt occurred before writing the revised article file. Subsequent checks ran against the actual revision.

Edge cases addressed

  • Unknown article slugs use existing not-found behavior.
  • Dedicated article lookup excludes unpublished entries.
  • Compact sizing defaults off for unrelated articles.
  • Both article and expanded preview receive the setting.
  • Smaller screens keep fluid image width; originals remain linked.
  • Uploaded checklist lines become separate content entries.
  • Raw article HTML is not interpreted.
  • Captions identify synthetic data and historical verification.

Rollback strategy

These changes concern content, component presentation, images, and a PDF. They require no database migration. Roll back through a normal revert commit and the usual merge/deployment workflow:

git revert <commit-to-undo>
# Run the relevant checks, review, then deploy normally.
  • Revert the copy revision to restore previous wording.
  • Revert the sizing change to restore previous image presentation.
  • Revert the visual addition to remove article images.
  • Handle dependencies carefully: do not remove image files while content still references them.

Use a revert, not a force-push of shared history. Reverting preserves the audit trail and creates a reviewable change.

12. Blog post extraction: the reusable engineering lesson

Place each rule where it can be enforced, and test each change at the layer where it can fail.

  • Route stability belongs in article identity.
  • Image presentation belongs in a reusable component.
  • Evidence claims must be grounded in source records.
  • Browser behavior must be checked in a browser.
  • A PDF should be inspected as an exported PDF.
  • A Git push and a production deployment are separate events.

The high-impact portfolio change

compactImages?: boolean;

// Default preserves existing callers:
compactImages = false

// Opt the intended article into the compact layout:
"mx-auto w-full max-w-[560px]"

This is a reusable technique: introduce a small capability with a backward-compatible default, then opt the intended caller into it.

The TurnFlow mechanism we explained

const claimed = await db
  .update(invites)
  .set({ status: "accepted", acceptedById: userId, acceptedAt })
  .where(
    and(
      eq(invites.id, invite.id),
      eq(invites.status, "pending")
    )
  )
  .returning({ id: invites.id });

if (claimed.length === 0) {
  return { error: INVITE_PROBLEM_MESSAGES.used };
}

The condition is evaluated as part of the database update. It avoids separately reading “pending” and later performing an unconditional write.

  1. Two requests try to claim the same invitation.
  2. The database checks pending status as part of the update.
  3. One request changes pending to accepted.
  4. The competing request cannot claim that accepted row.
  5. Surrounding signup operations still need their own failure handling.
Exact guarantee: only one request wins that invitation claim. This does not make account creation, assignment, and audit logging one transaction.

The strongest engineering habit in this work is precision: explain what a mechanism guarantees, verify that guarantee, and identify what remains outside it.
